## 二、各预订单位闭环检查

### 2.1 按小时预订 (`booking_unit = "hour"`)

**完整流程路径**：

```
创建预约 (create_booking)
  │
  ├── 验证 → resource存在、时间格式HH:MM、end > start
  ├── 冲突检测 → 同资源同时段活跃预约碰撞检测 (time overlap)
  │
  ├── 费用计算
  │   ├── 单价 = 用户身份定价 (base/member/vip)
  │   ├── 时长 = (end - start) 小时数
  │   ├── 总价 = 单价 × 时长
  │   └── 免费额度 → 扣除free_hours_per_month
  │
  ├── 支付决策
  │   ├── 内部/会员/VIP有余额 → balance_deduct (自动扣款)
  │   ├── 内部/会员/VIP余额不足 → mixed (部分扣+部分记账)
  │   ├── 内部/会员/VIP余额为零 → credit (全记账)
  │   └── 外部访客 → prepay (需审批+付款)
  │
  ├── 审批决策
  │   ├── 不需要审批 + 内部 → 自动 approved
  │   ├── 不需要审批 + 外部 → 自动 pending
  │   └── 需要审批 → pending (创建审批记录)
  │
  ├── 状态流转
  │   pending → approved/confirmed → active → completed → settled
  │                                                         │
  │                      ┌──────────────────────────────────┤
  │                      ▼                                  ▼
  │               已余额扣减 → 无需结算                记账模式 → 月度账单
  │
  └── 取消 → balance_deduct退款 → deposit_refunded
```

**✅ 闭环验证通过**

### 2.2 半天/场次/时段预订 (`half_day / session / slot`)

**差异点**：
- 依赖 `time_slot_key` 而非 `start_time/end_time`
- 冲突检测：同资源同日同时段活跃预约
- 时长取自 `ResourceTimeSlot.duration_value`
- 流程路径同上

**✅ 闭环验证通过**

### 2.3 日/周/月预订 (`day / week / month`)

**差异点**：
- 依赖 `end_date` 或 `booking_days` 计算多日跨度
- 冲突检测：日期范围重叠（`req_start <= ex_end AND ex_start <= req_end`）
- 时长换算：`day=天数` / `week=ceil(天数/7)` / `month=ceil(天数/30)`
- 流程路径同上

**✅ 闭环验证通过**

### 2.4 餐次预订 (`meal`)

**差异点**：
- 依赖 `meal_session`（如 "lunch"/"dinner"）+ `guests_count`
- 冲突检测：同资源同日同时餐次
- 费用计算：餐标 × 人数
- 收费三档：`meal_standard_price` / `meal_vip_price` / `meal_luxury_price`
- 流程路径同上

**✅ 闭环验证通过**

## 三、各角色闭环检查

### 3.1 内部员工（user_type=internal / member）

```
预约创建 → 自动检测余额
  ├── 余额≥费用 → 自动扣款 → 自动审批 → 可直接使用 → 完成 → 无需结算
  └── 余额<费用 → 部分扣款+记账 → 自动审批 → 使用 → 完成 → 月度账单结算
```

**⚠️ 问题 1：自动审批场景未区分空间价值等级**

当前实现：所有内部用户预约只要不需要人工审批（`requires_approval=False`），无论资源单价高低都**自动审批通过**。缺少按资源价值分级的配置机制。

**影响**：高价值空间（如总裁会议室）无法设独立审批门槛。

---

### 3.2 外部访客（user_type=external）

```
预约创建 → pending（强制） → 管理员审批

  └── 审批拒绝 → rejected（附带原因）
```

**✅ 闭环验证通过**

### 3.3 办公室管理员（office_admin）

```
可管理本办公室资源
  ├── 资源CRUD（scope=本办公室）
  ├── 预约审批（scope=本办公室）  
  └── 资源启停（scope=本办公室）
```

**✅ 闭环验证通过**

### 3.4 审批与收款一体化

**功能**：`PUT /api/v2/space/bookings/{id}/approve-with-payment`  
适用于管理员接待外部访客线下付款的场景。

## 四、支付和结算闭环检查

### 4.1 余额抵扣链路

```
预约创建 → deduct_amount计算 → BalanceDeductRecord创建
  ├── membership_balance扣减（优先）
  ├── service_balance扣减（次优先）
  ├── gift_balance扣减（最后）
  ├── BalanceTransaction创建（3笔：每种余额各一笔）
  └── booking.deduct_record_id = deduct_record.id

取消预约 → 读取deduct_record → 原路退还 → 创建退款Transaction
```

**✅ 闭环验证通过**

### 4.2 记账模式 → 月度账单链路

```
预约创建 → credit模式 → 记入credit_amount
  │
预约完成 → admin触发settle
  │
  ├── CreditNoteItem创建（对应单条预约）
  ├── CreditNote创建/更新（按月汇总）
  └── status → settled

管理员 → POST /api/v2/space/payment/monthly-settlement
  ├── 按月份批量处理
  ├── 批量设置 status → settled
  └── credit_note.paid_amount 更新
```

**⚠️ 问题 2：月度结算未校验预约是否已完成**

当前 `process_monthly_settlement` 直接对所有符合条件的 CreditNote 执行结算，但未逐项校验关联的 SpaceBooking 是否至少处于 `completed` 或 `settled` 状态。如果管理员误操作，可能将尚未完成的预约也结算入账。

**影响**：结算数据准确性依赖管理员操作流程，缺少系统级防护。

### 4.3 免费额度管理

```
每月初始化 → UserSpaceQuota（按user+type+month）
  │
预约创建（hour单位） → 检查剩余额度
  ├── 有剩余 → 按比例抵扣总价
  ├── 更新 quota.free_quota_used
  └── 更新 quota.free_quota_remaining

跨月 → 自动滚动（每月创建新额度行）
```

**✅ 闭环验证通过**

### 4.4 押金管理

```
空间类型配置 requires_deposit + deposit_percentage
  │
预约创建 → deposit_amount = total_fee × deposit_percentage
  ├── deposit_paid = false（初始）
  ├── 管理员确认 → deposit_paid = true
  │
取消预约 → deposit_refunded = true（自动标记）
  └── 但：实际退款操作需线下进行，系统仅做登记
```

**⚠️ 问题 3：押金登记为纯标记，无实际资金流管理**

系统对押金的管理仅为布尔标记（`deposit_paid` / `deposit_refunded`），没有押金专用账户或资金流水记录。管理员操作界面依赖人工核对。在频繁押金场景下容易产生账实不符。

**影响**: 押金的收取和退还均依赖线下操作，系统缺少押金台账管理能力。

## 六、发现的问题汇总

### 🔴 问题 1：自动审批缺少价值分级

- **位置**: `apps/api/v2/space_bookings.py`，`create_booking` 方法
- **描述**: 当 `requires_approval = false` 时，所有内部员工预约都自动审批通过，没有按资源价值分级的配置机制（如总费用超过 ¥1000 需人工审批）。
- **影响范围**: 高价值空间管控
- **建议修复**: 在 SpaceType 或 SpaceResource 上增加 `auto_approval_max_amount` 字段，超限后回退到人工审批。

### 🔴 问题 2：月度结算缺少前置校验

- **位置**: `apps/api/v2/space_payment_settlement.py`，`process_monthly_settlement` 方法
- **描述**: 结算时未逐项验证关联预约是否已完成/可结算。
- **影响范围**: 结算数据准确性
- **建议修复**: 结算前遍历 CreditNoteItem 检查关联 SpaceBooking.status 必须为 `completed` 或 `settled`。

### 🟡 问题 3：押金管理为纯标记登记

- **位置**: `shared/models/space/space_booking.py`，`deposit_paid` / `deposit_refunded`
- **描述**: 押金仅为布尔标记，无独立押金账户/流水/台账。收取和退还需线下操作。
- **影响范围**: 频繁押金场景操作复杂，易账实不符
- **建议修复**: 建立 `DepositRecord` 独立模型，记录押金流水。

### 🟡 问题 4：非小时类预订未使用免费额度

- **位置**: `apps/api/v2/space_bookings.py`，`create_booking` 方法
- **描述**: 免费额度抵扣逻辑仅对 `booking_unit == "hour"` 生效。`half_day` / `session` / `slot` / `day` 等不参与免费额度抵扣，但部分场景（如半日会议室）用户也应享有免费额度。
- **影响范围**: 用户感知的公平性
- **建议修复**: 允许 SpaceType 配置 `free_quota_applicable_units` 列表，控制哪些单位可使用免费额度，或按价值比例折算。

### 🟢 问题 5：需要审批 + 余额充足的内部场景状态模糊

- **位置**: `apps/api/v2/space_bookings.py`，`create_booking` 方法（约第 560 行左右）
- **描述**: 当 `requires_approval = True` 且用户为内部员工且有余额时，代码设置了 `initial_status = "pending"` 但 `payment_status` 保留为扣款后的值。这意味着余额已被扣减但预约仍处于待审批状态——如果审批被拒绝，余额已扣减（退款通过取消流程处理），用户感知上可能困惑。
- **影响范围**: 用户体验
- **建议修复**: 如果空间类型需要审批，余额扣减应推迟到审批通过后进行，或在前端审批流程中清晰展示"余额将保留"的提示。

## 八、总结

### 总体评价

本系统的空间预约流程在**核心业务路径上已实现完整闭环**，覆盖了：

- 8 种预订单位 × 4 种用户身份 × 3 种记账模式的全排列

- 余额扣减 + 记账 + 月度结算的支付结算链路

### 需要优先修复的问题

1. 🔴 **自动审批价值分级** — 高价值空间应支持独立审批门槛配置
2. 🔴 **月度结算前置校验** — 防止未完成预约被结算入账
3. 🟡 **押金管理升级** — 从纯标记升级为独立台账
4. 🟡 **免费额度适用范围** — 配置化支持非小时类额度抵扣
5. 🟢 **待审批余额扣减体验** — 需要审批的预约应推迟扣款
